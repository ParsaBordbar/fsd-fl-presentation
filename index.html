Where That Breaks

The usual recipe: gather everyone's data in one place, train the model there

That one pile hits hard walls: legal, ethical, and practical. One pile of data means one target and one owner.

Regulation

data cannot cross institutions or jurisdictions under GDPR and health law

User Trust

your keyboard sees secrets you do not expect on a vendor server

Volume

moving raw camera or sensor data from millions of devices is impractical

Blocked Projects

cross-hospital diagnosis models, fraud detection, EV range prediction all stall

@5 · 1 min

The Running Example

Centralized: the project cannot happen.
Federated: the project becomes possible.

Three hospitals want one shared model that reads a clinical note and picks the right department. Each holds valuable patient records. None can upload them to a central server — regulation, ethics, and patient trust all forbid it.

Without federated learning, the collaboration is blocked. With it, each hospital trains locally and shares only updates. The model improves. The records never move.

The sizes on the diagram are the demo's: 100, 300, 600. They come back on the live slide.
@6 · 1.5 min

One Round, Five Steps

Model goes out + local training + updates return + aggregate + repeat
The raw data stays with each participant
  1. Initialize the global model
  2. Send it to selected clients
  3. Train briefly on local data
  4. Return the update — how much the model's numbers changed — not the records
  5. Aggregate a new global model · repeat until convergence

@12.5 · 1.5 min

Read the Promise Carefully

"Your data never leaves your device" · The update does leave · Gradient inversion reconstructs training data
The raw record stays. The gradient computed from it travels.

Gradient is just the name for the update. Gradient inversion: guess the original input → run the same model → compare the resulting update → adjust the guess until the updates match.

When they match, the guess may reveal what was in training.

Sources: Zhu, Liu & Han 2019; Geiping et al. 2020.

Also, in one breath: the trained model leaks too. Membership inference (Shokri et al. 2017) tells whether a record was in the training set — for a psychiatric-hospital model, membership is the diagnosis.

@15.5 · 1.5 min

The Real Protections

Federated learning changes where training happens. Privacy must be actively added — it does not come for free.

Input Privacy

Secure aggregation: each hospital adds a random mask to its update; the masks cancel when summed, so the server sees only the total

Record vs Person

Privacy can protect one record or one person — these are not the same thing

Output Privacy

Differential privacy: cap what one record can change, add random noise on top, keep count of how much was revealed (the "budget")

Who Adds Noise?

The server, the client, or a trusted third party — the answer changes the guarantee

@17 · 1 min

No Free Privacy

σ = 0 → 99%
σ = 1.0 (Flower's "strong privacy") → 65%
σ = 4 → 37%, where chance is 33%

σ is the noise knob: clip every hospital's update to 0.5 and add random noise σ × 0.5 before averaging. More noise, more privacy, less accuracy. Same run, same data. Someone sets this knob — and reports it, or doesn't.

python fedavg_numpy.py --iid --noise 1.0

Global accuracy after 10 rounds vs DP noise multiplier · clip 0.5 · IID

On the non-IID case mix the collapse starts at σ = 0.25. Bridge to the next slide: the setting is the claim.
@18 · 1.5 min

Writing
to the Model

Federation lets every participant influence the shared model — and that is a threat surface:

01

Data Poisoning

A participant submits corrupt training examples, steering the global model toward a desired wrong output.

02

Model Poisoning

A participant crafts a malicious update directly — bypassing local data — to manipulate model weights.

03

Sybil Attack

One attacker registers many fake clients to amplify their influence over the aggregation step.

04

Backdoor

Ordinary inputs → ordinary behaviour; a hidden trigger → the attacker's output. Clean accuracy unchanged, so your test set may not catch it (Bagdasaryan et al. 2020).

@19.5 · 1.5 min

Defences — and Why They Conflict

Robust aggregation → throw away updates that look unlike the others (Krum, Bulyan, trimmed mean)
Secure aggregation → server cannot see individual updates
Robust aggregation → server must inspect individual updates

You usually cannot have both at full strength. Secure aggregation hides updates from the server; robust aggregation requires the server to inspect them. Add update-size limits, authentication, and reproducible training — but an honest minority client can still resemble an attacker.

@22.5 · 1.5 min

How to Audit the Claim

  1. Is the client free software?
  2. Is aggregation code published?
  3. Is secure aggregation enabled — how many hospitals must drop out before the server can unmask the rest?
  4. Does the privacy protect one record or one person, and how much leaks over the whole run (the total budget)?
  5. Who controls the aggregator and receives the model?
  6. Can the community fork and run its own federation?
"We use privacy protections" is a category, not a claim
Federated · secure aggregation · differential privacy — true labels, weak settings
Noise too low · budget per round, not totalled · unmasking threshold too low

A company may truthfully claim all three and still protect little. The settings behind the labels decide everything; without auditable parameters the promise cannot be verified. Six questions get you the parameters.

This is the answer to "how would you check" from slide 2. Six questions, all answerable only with free software.

The Question Is Fork

A federation running free software
Privacy settings chosen by participants
The right to fork — always

Architecture alone does not solve copyright, consent, group fairness, or evaluation-data ownership. The question is not only whether AI can learn without moving our data — it is whether the people producing that data can inspect, modify, govern, and fork what is built from it.
