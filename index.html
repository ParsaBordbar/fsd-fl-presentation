7 — Reverse the Pipeline

Centralized ML: move data to computation
Federated learning: move computation to data

Receive the global model → improve it locally on your own data → send back only a focused update, not the raw data.

The Running Example

Centralized: the project cannot happen.
Federated: the project becomes possible.

Three hospitals want one shared cancer-detection model. Each holds valuable patient records. None can upload them to a central server — regulation, ethics, and patient trust all forbid it.

Without federated learning, the collaboration is blocked. With it, each hospital trains locally and shares only updates. The model improves. The records never move.

@9 · 1.5 min

9 — One Round, Five Steps

Model goes out + local training + updates return + aggregate + repeat
The raw data stays with each participant
  1. Initialize the global model
  2. Send it to selected clients
  3. Train briefly on local data
  4. Return model updates, not records
  5. Aggregate a new global model · repeat until convergence
@10.5 · 1.5 min

Aggregation and Why It Is Weighted

100 clients → 100 different updates
The server needs exactly one model.

FedAvg averages updates weighted by each client's number of examples.

If client A has 10 examples and client B has 100, unweighted averaging makes each of A's examples count ten times more. Weighting gives every individual training example equal influence over the final model.

Source: McMahan et al., 2017

Weighting by data volume is also a decision about whose data counts most. That returns on the demo and at the end.

13 — Read the Promise Carefully

"Your data never leaves your device" · The update does leave · Gradient inversion reconstructs training data
The raw record stays. The gradient computed from it travels.

Gradient inversion: guess the original input → run the same model → compare the resulting update → adjust the guess until the updates match.

When they match, the guess may reveal what was in training.

Sources: Zhu, Liu & Han 2019; Geiping et al. 2020.

@15.5 · 1 min

The Model Leaks Too

The trained model is distributed to all clients
Membership itself can be the sensitive secret

Even if individual updates are protected, the trained model is sent to every participant. Membership inference attacks determine whether a specific record was used in training — just from observing model behavior.

For a psychiatric-hospital model, knowing someone was in the training set reveals a diagnosis.

Source: Shokri et al., 2017.

15 — The Real Protections

Federated learning changes where training happens. Privacy must be actively added — it does not come for free.

Input Privacy

Secure aggregation: individual updates are masked; masks cancel in the sum

Record vs Person

Privacy can protect one record or one person — these are not the same thing

Output Privacy

Differential privacy: limit contribution, add calibrated noise, track total budget

Who Adds Noise?

The server, the client, or a trusted third party — the answer changes the guarantee

@18 · 1.5 min

16 — The Ordinary Limits

• Non-IID data
• Bandwidth costs
• Device dropout

More privacy noise = less utility — there is no free privacy
  • Client data is not identically distributed — local models drift.
  • Updates can reach hundreds of MB per client per round.
  • Devices disconnect mid-round; fast clients wait for slow ones.
  • Average accuracy hides failure for small hospitals or underrepresented groups.
  • Adding differential privacy noise reduces model utility. These limits do not cancel federated learning — they mean it must be designed honestly.

All three are measured on slide 20: drift, the small hospital, the noise curve.

@19.5 · 1.5 min

Writing
to the Model

Federation lets every participant influence the shared model — and that is a threat surface:

01

Data Poisoning

A participant submits corrupt training examples, steering the global model toward a desired wrong output.

02

Model Poisoning

A participant crafts a malicious update directly — bypassing local data — to manipulate model weights.

03

Sybil Attack

One attacker registers many fake clients to amplify their influence over the aggregation step.

04

Byzantine Fault

Arbitrary malicious or broken updates — whether from attackers or faulty devices — corrupt the aggregate.

@21 · 1.5 min

19 — Backdoors

Bagdasaryan et al. · AISTATS 2020
Ordinary inputs → ordinary behavior
Hidden trigger → attacker-chosen output
Clean accuracy can remain unchanged

A backdoored model behaves normally on standard inputs. When a hidden trigger is present, it produces an output chosen by the attacker. Because clean accuracy is unchanged, your test set may not catch this.

The server also selects the model architecture, starting weights, and which participants are included each round.

@22.5 · 1.5 min

Defences — and Why They Conflict

Robust aggregation → discard outliers (Krum, Bulyan, trimmed mean)
Secure aggregation → server cannot see individual updates
Robust aggregation → server must inspect individual updates

You usually cannot have both at full strength. Secure aggregation hides updates from the server; robust aggregation requires the server to inspect them. Add update-size limits, authentication, and reproducible training — but an honest minority client can still resemble an attacker.

σ = 0 → 99%

@29.5 · 1.5 min

20 — The Claim Is in the Settings

Noise too low · Budget per round, not totaled · Unmasking threshold too low
Privacy protects one record, not one person · Client sends extra telemetry

A company may truthfully claim federated learning, secure aggregation, and differential privacy — and still provide weak protection. The settings behind those labels determine everything. "We use privacy protections" is a category, not a complete claim. Without auditable parameters, the promise cannot be independently verified.

@31 · 1.5 min

How to Audit the Claim

  1. Is the client free software?
  2. Is aggregation code published?
  3. Is secure aggregation enabled — what is the unmasking threshold?
  4. What is the privacy unit and total budget across the whole run?
  5. Who controls the aggregator and receives the model?
  6. Can the community fork and run its own federation?

Inspect

read the client, read the aggregator

Verify

threshold, unit, budget — numbers, not labels

Govern

who runs the server, who gets the model

Fork

the right to run your own federation

This is the answer to "how would you check" from slide 3. Six questions, all answerable only with free software.

The Question Is Fork

A federation running free software
Privacy settings chosen by participants
The right to fork — always

Architecture alone does not solve copyright, consent, group fairness, or evaluation-data ownership. The question is not only whether AI can learn without moving our data — it is whether the people producing that data can inspect, modify, govern, and fork what is built from it.
